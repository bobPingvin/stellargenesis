## 2. Конкретные замечания и рекомендации по результатам ревью

### Комментарий 1: Разграничение размера бандла при передаче по сети (Gzip) и на диске (Raw Size)
- **Категория:** Метрики производительности
- **Суть замечания:**
  В таблице отчёта команды указан размер бандла: «Целевое: $\le 500$ KB | Факт: 320 KB». При этом на приложенном скриншоте `network.png` видно, что 320 KB — это размер распакованных ресурсов на диске (`Resource Size`), а реальный вес переданного по сети архива (`Transferred Size`) составил всего 94 KB gzip.
- **Рекомендация:** 
  Четко указывать в графе «Факт» обе величины: сетевой трафик (`Transferred: 94 KB gzip`) и объем в памяти браузера (`Parsed JS: 320 KB`), так как для мобильных пользователей решающее значение имеет именно transferred gzip, а для времени выполнения на слабых процессорах — parsed JS.

---

### Комментарий 2: Достоверность измерения плотности дефектов (Defect Density)
- **Категория:** Метрики качества и тестирования
- **Суть замечания:**
  В отчёте указано: «Плотность багов: 4.7 на 1000 строк при норме $\le 5$». При этом в формуле расчета количество багов (4) поделено на 850 строк кода. Математический расчёт дает:  
  $$\text{Плотность} = \frac{4}{0.850\text{ KLOC}} = \mathbf{4.71\text{ бага/KLOC}}$$
  Расчёт выполнен верно, однако в кодовой базе не учтены тестовые файлы (`tests/*.test.js`). 
- **Рекомендация:**
  Явно указать в примечании к таблице, какой именно объем строк учитывался (только исполняемый код `src/` без тестов), так как включение тестов снижает номинальную плотность багов.

### Комментарий 3: Методика замера цикломатической сложности ($V(G)$)
- **Категория:** Метрики сложности кода
- **Суть замечания:**
  В отчёте заявлена средняя цикломатическая сложность «6» при норме $\le 10$. Однако в описании инструментария не указано, какой плагин или правило ESLint использовалось для замера (например, `eslint-plugin-sonarjs` или встроенное правило `complexity`). Без указания инструмента значение выглядит экспертной оценкой, а не инструментальным замером.
- **Рекомендация:**
  Добавить команду запуска линтера с флагом правила сложности, например:  
  `npx eslint src/ --rule '{"complexity": ["error", 10]}'` для воспроизводимости результатов аудита.

### Комментарий 4: Конкретизация инженерных рекомендаций по оптимизации
- **Категория:** Рекомендации и план улучшений
- **Суть замечания:**
  В разделе рекомендаций пункт №3 сформулирован абстрактно: «Уменьшить размер бандла: минифицировать JS». Поскольку в проекте уже используется современный сборщик Vite, минификация через `esbuild` / `terser` включена по умолчанию. Причиной размера бандла является не отсутствие минификации, а импорт неиспользуемых иконок и библиотек.
- **Рекомендация:**
  Заменить абстрактную рекомендацию на конкретную: «Настроить Tree-shaking для пакетов иконок и применить динамический импорт (`React.lazy()`) для административной панели директора».
