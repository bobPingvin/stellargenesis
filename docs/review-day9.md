## Введение и цель ревью

В соответствии с регламентом Дня 9 практики проведена перекрестная экспертиза качества тестовых артефактов команды №2. Цель рецензирования — выявить несоответствия между протоколами, тест-кейсами и баг-репортами, проверить воспроизводимость описанных шагов, реалистичность фактических замеров и корректность классификации серьезности дефектов.

## Конкретные замечания и рекомендации по результатам ревью

### Комментарий 1: По структуре и формулировкам тест-кейсов (Test Cases)
- **Проверяемый артефакт:** `docs/test-cases.md`, тест-кейсы TC-03 («Бронирование/захват занятого слота») и TC-07 («Отображение параметров объекта»).
- **Суть замечания:**
  В шагах воспроизведения кейса TC-03 используется неконкретное действие: *«Попробовать занять объект №2 повторно»*, без указания конкретного состояния системы. Не указано предусловие: кем именно занят объект, в каком статусе находится сессия (активна, завершена или в режиме ожидания) и какие координаты/временные метки передаются на вход.
  В кейсе TC-07 в графе «Ожидаемый результат» написано общее утверждение: *«Данные должны отображаться корректно»*. Тестировщик не имеет четкого критерия успешности: какие именно параметры обязаны быть в карточке (числовые диапазоны, единицы измерения СИ, валидация отсутствия `null`/`undefined`).
- **Рекомендация по исправлению:**
  1. Переписать шаг TC-03 с детерминированными входными данными:
     - Предусловие: `Объект ID=02 переведен в статус RESERVED пользователем User_A с таймстемпом t0`.
     - Шаг: `Авторизоваться под User_B, выбрать объект ID=02, нажать кнопку "Забронировать"`.
  2. В TC-07 перечислить исчерпывающий перечень проверяемых полей и их допустимые типы данных (например: `Масса: положительное число с плавающей точкой, Радиус: целое > 0, Статус: enum ['active', 'reserved']`).

### Комментарий 2: По фиксации фактических результатов в протоколах (Factual Results)
- **Проверяемый артефакт:** `docs/test-protocols.md`, проверки TC-01, TC-04, TC-11.
- **Суть замечания:**
  В протоколах ручного тестирования по кейсам TC-01 и TC-11 в графе «Фактический результат» оставлены лаконичные формулировки: *«Карта отобразилась, всё работает (PASS)»* и *«Ошибок нет»*.
  Такая запись не подтверждает реального факта инструментального замера. Не зафиксированы критически важные метрики производительности:
  - Каково реальное время отрисовки DOM/Canvas (в миллисекундах по вкладке DevTools Performance)?
  - Какова частота кадров (FPS) при рендере объектов на холсте?
  - Были ли обращения к сети (вкладка Network) и с какими статус-кодами (200 OK / 304)?
- **Рекомендация по исправлению:**
  Заменить качественные оценки измеримыми количественными фактами по аналогии с лучшими практиками QA:
  - Вместо *«Карта отобразилась»* указать: *«Время холодного рендера составило 1.34 с (Performance DOMContentLoaded = 420 мс). Отрисовано ровно 18 сущностей. Частота кадров 59.4 FPS, утечек памяти по Heap Snapshot не зафиксировано (куча стабильна на уровне 22.1 МБ). Вкладка Console содержит 0 warnings / 0 errors»*.

### Комментарий 3: По классификации серьезности и привязке баг-репортов (Bug Reports & Severity)
- **Проверяемый артефакт:** `docs/bug-reports.md`, дефекты BR-01 и BR-03.
- **Суть замечания:**
  1. **Некорректная классификация критичности (Severity):** Дефекту BR-01 (*«Не сохраняются данные формы при случайном клике мимо модального окна»*) присвоен статус **«Критический (Critical)»**, в то время как дефекту BR-03 (*«При падении WebGL-контекста всё приложение падает в белый экран без возможности восстановления»*) присвоен статус **«Средний (Medium)»**. 
     Это грубая инверсия приоритетов: потеря контекста рендера блокирует 100% функционала симулятора (Showstopper / Blocker), в то время как закрытие модалки при клике на оверлей — это типовой минорный UX-дефект.
  2. **Отсутствие диагностических логов:** Ни в одной карточке бага нет прикрепленного стектрейса ошибки из консоли браузера или скриншота сетевой ошибки.
- **Рекомендация по исправлению:**
  1. Повысить критичность BR-03 до **Blocker / Critical**, так как сбой WebGL приводит к полному отказу приложения (`Uncaught TypeError: Cannot read properties of null (reading 'getExtension')`).
  2. Понизить BR-01 до **Medium / Low (UX)**.
  3. В каждую карточку бага добавить блок `Environment & Console Output` с точным текстом ошибки и файлом/строкой кода, где упал скрипт.

### Комментарий 4: По шагам воспроизведения дефектов (Steps to Reproduce)
- **Проверяемый артефакт:** `docs/bug-reports.md`, дефект BR-02 (*«Сумма рассчитывается неверно»*).
- **Суть замечания:**
  Шаги воспроизведения в текущей редакции сформулированы так:
  1. *«Выбрать несколько объектов»*;
  2. *«Нажать расчет»*;
  3. *«Посмотреть итоговую сумму — она не сходится»*.
  
  По такой инструкции баг **невозможно воспроизвести** стороннему инженеру или разработчику:
  - Не указано, какие именно объекты были выбраны (ID, тарифный план, базовая стоимость);
  - Не указан выбранный интервал времени или коэффициенты нагрузки;
  - Не приведена математика расхождения: какая сумма ожидалась по тарифной сетке и какая сумма фактически отобразилась на экране (например, ожидалось `1200 ₽`, отобразилось `NaN` или `1000 ₽`).
- **Рекомендация по исправлению:**
  Оформить шаги строго по шаблону детерминированного воспроизведения:
  ```markdown
  Шаги воспроизведения:
  1. Очистить LocalStorage (`localStorage.clear()`) и обновить страницу.
  2. Добавить в корзину объект ID=03 (базовый тариф 500 ₽/час).
  3. Указать длительность аренды: 3 часа (коэффициент 1.0).
  4. Применить промокод "STUDENT10" (-10%).
  Ожидаемый результат: Итоговая стоимость = (500 * 3) * 0.9 = 1350 ₽.
  Фактический результат: Отображается строка "5003 ₽" (происходит строковая конкатенация вместо сложения чисел `500 + "3"`).
  ```

### Комментарий 5: По соответствию итоговой сводки протоколам (Summary vs Protocols Consistency)
- **Проверяемый артефакт:** Сверка `docs/test-protocols.md` и `docs/test-summary.md`.
- **Суть замечания:**
  Обнаружено прямое численное расхождение между протоколами и сводкой:
  - В файле `docs/test-summary.md` в таблице метрик указано:
    *«Всего тест-кейсов: 20. Успешно: 17. Не пройдено: 3»*.
  - При сплошном подсчете строк в `docs/test-protocols.md` фактически описано **22 тест-кейса** (присутствуют кейсы TC-21 и TC-22, которые не учтены в сводке).
  - При этом в протоколах статус ❌ («Не пройден») имеют кейсы TC-03, TC-09, TC-14 и TC-18 — то есть **4 непройденных кейса**, а не 3, как заявлено в сводке.
  - Кроме того, в баг-репортах заведено 5 дефектов (BR-01..BR-05), в то время как в сводке указано суммарно 3 дефекта.
- **Рекомендация по исправлению:**
  Провести полную реконсиляцию метрик:
  1. Синхронизировать общее число кейсов: строго $N = 22$.
  2. Актуализировать число непройденных проверок в сводке: 4 FAIL (соответствуют зарегистрированным багам).
  3. Указать четкую трассируемость: каждый проваленный тест-кейс обязан ссылаться на конкретный ID баг-репорта (например, `TC-03 -> BR-01`, `TC-09 -> BR-02`, `TC-14 -> BR-03`, `TC-18 -> BR-04`).
