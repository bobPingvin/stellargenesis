## 2. Конкретные замечания и рекомендации по результатам ревью

### Комментарий 1: Проверка на ошибки и исключения (Negative Testing & `toThrow`)
- **Проверяемый файл:** `tests/pricing.test.js`, функция `calcPrice()`.
- **Суть замечания:**
  В наборе присутствует тест:
  ```javascript
  it('должен выбросить ошибку при hours <= 0', () => {
    expect(() => calcPrice(1, 0)).toThrow();
  });
  ```
  Использование универсального матчера `.toThrow()` без аргументов является антипаттерном. Тест станет «зеленым», даже если функция упадет с непредвиденной синтаксической ошибкой `TypeError: Cannot read properties of undefined` или опечаткой в переменной, а не с валидационным исключением бизнес-логики.
- **Рекомендация по исправлению:**
  Всегда проверять тип исключения или конкретный текст сообщения об ошибке:
  ```javascript
  expect(() => calcPrice(1, 0)).toThrowError(/Количество часов должно быть положительным числом/);
  // или по классу кастомной ошибки:
  expect(() => calcPrice(1, 0)).toThrow(ValidationError);
  ```

### Комментарий 2: Полнота покрытия критической бизнес-логики (Edge Cases & Boundary Values)
- **Проверяемый файл:** `tests/booking.test.js`, функция `isSlotAvailable()`.
- **Суть замечания:**
  Проверяются только два тривиальных сценария: «слот свободен» и «слот занят активной бронью». При этом полностью проигнорированы граничные условия:
  1. Пересечение временных интервалов (например, бронь с 12:00 до 14:00, а новый запрос на 13:00–15:00);
  2. Разрешение коллизий при переходе через полночь (стык календарных суток);
  3. Поведение функции при передаче невалидного формата даты (`'2026-02-31'`, `'null'`, пустая строка).
- **Рекомендация по исправлению:**
  Добавить в блок `describe('isSlotAvailable')` минимум 3 негативных и граничных теста:
  - Проверка частичного перекрытия временного слота;
  - Проверка валидации формата ISO 8601;
  - Проверка обработки часовых поясов (UTC vs Local Time).

### Комментарий 3: Качество и читаемость названий тестов (Test Naming Conventions)
- **Проверяемый файл:** `tests/dateValidator.test.js`.
- **Суть замечания:**
  В наборе встречаются названия тестов вида:
  - `it('test 1', () => { ... })`
  - `it('check date function', () => { ... })`
  - `it('works with weekend', () => { ... })`
  
  Такие названия не дают никакой информации при падении тестов в CI/CD пайплайне. Инженеру приходится открывать исходный код теста, чтобы понять, какой именно бизнес-кейс нарушен.
- **Рекомендация по исправлению:**
  Следовать стандарту BDD-именования (Given-When-Then или «должен [ожидаемое действие], если [условие]»):
  - `it('должен возвращать true для рабочих дней (понедельник-пятница)', () => { ... })`
  - `it('должен применять праздничный тариф 1.5x для дат производственного календаря', () => { ... })`
  - `it('должен выбрасывать RangeError при передаче даты в прошедшем времени', () => { ... })`

### Комментарий 4: Изоляция состояния и утечки между тестами (Test Isolation & Side Effects)
- **Проверяемый файл:** `tests/booking.test.js`.
- **Суть замечания:**
  Функция `createBooking()` внутри модифицирует глобальный `localStorage`, однако очистка хранилища выполняется только в хуке `beforeEach()`. Если один из тестов упадет в середине выполнения, последующие тесты в других файлах могут получить «загрязненное» окружение при параллельном запуске воркеров Vitest.
  Кроме того, не восстанавливаются системные таймеры при работе с `Date.now()`.
- **Рекомендация по исправлению:**
  1. Добавить хук `afterEach(() => { localStorage.clear(); vi.restoreAllMocks(); })`.
  2. Использовать `vi.useFakeTimers()` для заморозки текущей даты при тестировании бронирований, чтобы тесты не зависели от даты их запуска.

### Комментарий 5: Достоверность отчета о покрытии (`docs/test-coverage.md`)
- **Проверяемый артефакт:** `docs/test-coverage.md`.
- **Суть замечания:**
  В отчете заявлено «Покрытие функций: 85%». При этом в репозитории отсутствует запуск встроенной утилиты сбора покрытия (`vitest --coverage` на базе `@vitest/coverage-v8`). Значение 85% проставлено вручную без табличной разбивки по строкам (Lines), ветвлениям (Branches) и функциям (Functions).
- **Рекомендация по исправлению:**
  Установить пакет `@vitest/coverage-v8`, добавить скрипт `"test:cov": "vitest run --coverage"` и приложить реальную сгенерированную консольную таблицу с метриками `Stmts | Branch | Funcs | Lines`. Либо честно указать в заголовке, что это экспертная оценка покрытия спецификации, как это принято в инженерных стандартах.
